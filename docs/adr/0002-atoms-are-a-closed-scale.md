# Atoms are a closed scale; one-off values belong in consumer styles

An Atom takes only values from a fixed set: a theme's token scale or a few literal values. Atoms never accept arbitrary values at runtime, and a set doesn't grow to cover one consumer's layout. A value is added only when it comes from a token scale, when Blocks' own components need it, or when it is a CSS keyword (or a reset like `0`) that apps commonly need, such as the `grab`, `grabbing`, `text` and `not-allowed` cursors (T319), `minInlineSize: 0` to let a flex item shrink (T314), or `listStyle: none` to drop list markers (T313). A keyword set stays small and fixed, so it costs only a few classes, unlike the scale-sized sets rejected below. One-off values, such as a 0.4 fade or a badge overhanging its anchor's corner, belong in the consumer's own styles: a `className` from their own stylesheet, or inline `style` for values only known at runtime. Every Atom value is compiled into a class in core's CSS, which every app ships, so open-ended sets would bloat the bundle for everyone. Runtime values would need inline custom properties, which ADR 0001 already rejected because they break under a strict CSP. A closed scale also keeps consumers on theme tokens.

This rule covers Atoms only. A component prop that takes keys from a token scale and compiles its classes for that one component alone, such as `GridItem`'s `colSpan`, is not an Atom. Every app still ships its classes, but the set is bounded by the scale and serves a layout the component itself owns, so it may be added for a single consumer.

Layouts that need a value outside the Atom scale become such a component prop instead, when the value still comes from a token scale. `Grid`'s `minColumnWidth` (T727) takes a `space` step from 1 to 8 and lays out `repeat(auto-fill, minmax(<space step>, 1fr))` columns, so an icon or swatch grid needs no consumer class. It is a single value, not responsive, and not an Atom: Atoms don't set `gridTemplateColumns`, and widths above the `space` scale stay consumer classes.

## Considered Options

- **A `muted` opacity step**: rejected. It was asked for in T320 for faded drag states, but it has no token scale behind it and only one consumer needs it.
- **Inset Atoms that take the `space` scale, negative steps included**: rejected. It was asked for in T320 to overhang a count pill. That would add a class for every space step on all six inset properties to serve one overlay.
- **Marker values for `listStyle`** (`disc`, `decimal`, …): rejected. No Blocks component draws list markers. The reset zeroes padding, so a marker value on its own would hang outside the list, and a usable set would also need a `listStylePosition` Atom. Visible markers belong in consumer or prose styles.
- **Arbitrary values through CSS variables**: rejected for the CSP reason above, and because it would turn Atoms into an untyped escape hatch.
